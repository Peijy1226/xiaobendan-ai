### 3. 毛玻璃是动态的

每 90ms 从视频壁纸的当前帧裁出面板那一块 → 缩到 1/3 → `GaussianBlur(3)` → 放大 →
压 44% 暖黑 → 贴回。壁纸在动，玻璃后面就跟着流动。

- 视频壁纸：每轮都重做（每帧都是新的）
- 静态壁纸：只在换图时做一次（省 CPU 不影响观感）

**代价是实打实的**：884×664 的图每 90ms 合成一次，约 15~20ms，加上 2K60 解码，
双核负载明显。要降温就把 `_dong_tai` 里的 `after(90, ...)` 改成 `after(200, ...)`。

### 4. 选中胶囊：22 帧预生成，流光裁在圆角里

上一版是一条光带贴在 Canvas 上横移，于是会**跑出按钮外面**。这一版改了做法：

- 一次性生成 22 帧完整胶囊（五段金属渐变 + 顶部高光 + 底部内阴影 + 外描边 + 柔光带）
- 每帧的流光都是**先合成再一起过圆角遮罩**，物理上不可能溢出
- 运行时只做 `itemconfigure(image=帧)`,单次 <1ms,不重算颜色

### 5. 十个图标

`_gn_tubiao()` 用 4 倍超采样画线性图标再缩回 16px（PIL 的线没有抗锯齿，直接画会一格一格）：
计算器、图片、笔、文件夹、心、画框、字母 A、垃圾桶、问号、i。选中时变深色，未选是灰。

### 6. 切页淡入

新内容层从 alpha 0 分 4 帧（26ms 一帧）淡到 1。
**不是"旧图新图交叉淡化"** —— 那样在动画没走完时切第二页，旧页会以半透明挂在上面
（实测在整理页残留过写作页的大框）。现在只让新内容自己淡进来，永远不会串页。

#### 换算到底算了什么

| 类 | 例子 | 输出 |
| --- | --- | --- |
| 汇率 | 100美元换人民币 | 100 美元 ≈ 710.00 人民币。离线参考汇率 1 美元 ≈ 7.1…（注明会过期） |
| 亲戚 | 妈妈的妹妹的老公怎么称呼 | 妈妈的妹妹的老公，叫「姨父」 |
| 单位 | 5公里等于多少米 / 8gb等于多少mb / 30摄氏度等于多少华氏度 | 5000 米 / 8192 mb / 86.0 华氏度 |
| 日期 | 3月5日到4月2日几天 | 28 天 |
| 百分比 | 200打八折 / 200的15% | 160.00 块（省 40）/ 30 |
| 进制 | 255转成十六进制 | FF |

单位名用已知表拼正则，**不能让 `{1,6}` 去猜** —— 贪婪会把"等于"一起吃进单位名，
查表查不到，整句就算不出来（第一版就是这么挂的）。

#### 顺手修的三个隐性问题

- **面板背景"对不上"**：原来底图和内容分两个 Canvas image 叠，实测出现
  `self.di` 是 95（暗）但屏幕上是 150（浅）的情况。现在合成成一张图再贴，
  屏幕显示的一定就是算出来的那张。
- **两个 90ms 定时器各重绘一次全图**：流光和底图各一个，白烧一倍 CPU，
  合并成一条链后单次 24ms / 90ms 周期（约 27% 一核）。
- **静态壁纸的压暗永远停在中途**：平滑系数只在视频时需要，静态壁纸只算一次，
  平滑让它卡在 0.46 —— 换成浅色壁纸后整块面板一片灰白。现在只对视频平滑。

#### 还没做的

- 识图的"画框"是在缩略图上按比例画的，不是原图另存。
- 打赏礼物只放了 10 个（`LIWU_BIAO` 全量），点一下直接送，不再弹旧窗。

#### 提速（没降任何画质参数）

卡顿的根源是"两张图各自在烧"：主窗口 2K60 视频贴帧 + 功能页每 90ms 重画整页。

| 手段 | 省了什么 |
| --- | --- |
| 内容层缓存 | 文字/卡片只在切页或点按钮时重画，换底图/换流光帧只做合成（原来每 90ms 把整页文字重画一遍，14ms） |
| 胶囊单独一层 | 流光换帧不再连带重建文字层；`_tie()` = 贴小胶囊 + 一次合成 ≈ 9~13ms |
| 面板打开时主窗跳过贴图 | 主窗口每帧省 11ms 的 PhotoImage+create_image，只留最新帧给面板；面板一关自动恢复 |
| `_zuo_di` 少一次全图合成 | 描边直接画在 RGB 上再过圆角遮罩，省 4ms 的 alpha_composite |

实测单帧合成降到 ~9ms（原来 24ms），主窗口贴图省 11ms/帧。**壁纸帧率、模糊半径、压暗系数这些一个没动。**

属于要加人设句子的活，没做。

**又抓到一个老 bug**：话题表里「怎么办」被当成“选择困难”的关键词（`("自由","选择","纠结","怎么办","要不要")`），
所以「很焦虑怎么办」会被答成“纠结通常不是因为两个选项都好”。已把「怎么办」从该组和“求助组”里摘掉 ——

### 5. 为什么用 ctypes 而不是 send2trash

`send2trash` 是第三方包，打成 exe 要多塞一个依赖；`SHFileOperationW` 是系统自带的
shell32，零依赖，和现有打包方式（只 collect rapidocr/onnxruntime）不冲突。
一个文件一次调用，不打包成一串 —— 批量送的时候只要有一个失败，返回值说不清是谁的错。
调完还要复查 `os.path.exists()`：`FOF_ALLOWUNDO` 在某些情况下（跨卷、文件被占用）
会静默不动，返回 0 不代表文件真走了。

### 7. 删除过程放进 cmd 窗口，删完自动打开回收站（本轮追加）

老师要求"删除时要有 cmd 弹窗展示过程，自动打开回收站"。做法不是把进度打印到 GUI
里假装，而是**真的开一个控制台窗口跑子进程**：

| 角色 | 干什么 |
| --- | --- |
| 主窗口 | 确认后只写一份清单（`%TEMP%\小笨蛋_整理清单.txt`），拉起子进程，然后每 400ms 数一次结果 |
| 子进程 | `python 小笨蛋.py --整理删除 清单`（`CREATE_NEW_CONSOLE` 给一个新控制台），逐个移文件，边做边打印 |

窗口里长这样（实测截屏）：

```
==========================================================
  小笨蛋 · 整理助手
  只把文件移到回收站，不是直接删除
==========================================================
文件夹：C:\Users\study\小笨蛋演示夹
一共 5 个文件，合计 7.0 KB
----------------------------------------------------------
[1/5] 压缩包_备份.zip  (1.8 KB)
        √ 已移入回收站
[2/5] 安装包_某播放器安装程序.exe  (3.1 KB)
        √ 已移入回收站
...
----------------------------------------------------------
成功 5 个，失败 0 个
正在打开回收站……
按任意键关闭窗口（20 秒后自动关）
```

三个设计决定：

- **父子靠结果文件传话**，不解析屏幕文字：子进程每移完一个就往
  `%TEMP%\小笨蛋_整理结果.txt` 追一行 `OK\t路径` / `ERR\t路径\t原因`。改文案不会影响逻辑。
- **界面不等窗口关**：窗口要留 20 秒给人看，等它退出界面上就干等 20 秒。
  所以主窗口按"结果条数到齐"就收工（实测 2.0 秒回面板），窗口自己在那里倒计时。
- **窗口自己会走**：按任意键提前关，不按 20 秒自动关（`msvcrt.kbhit` 轮询）。

### 8. 两个必须写下来的坑（都在这轮踩到）

1. **`SHFileOperationW` 的返回码不能当判据。** 回收站里已有同名文件时，系统**照样
   把文件搬走**，却返回 `2`（看着像"找不到文件"）。第一次实测就撞上：屏幕上 5 个
   全报"失败"，回收站里 5 个都在。现在判据改成**先看文件还在不在**，返回码只在真的
   没搬走时拿来说明原因。
2. **路径里的正斜杠会让它直接报错 2。** `C:/Users/...` 这种写法 `SHFileOperationW`
   不认（`os.path` 拼出来常常是混合斜杠）。现在写清单时统一 `os.path.abspath()`，
   子进程读进来再过一次，保证是反斜杠绝对路径。

### 10. 已知限制

- **没有"撤销上一次"**：还原要靠回收站（按钮能直接打开，删完也会自动弹出来）。做撤销需要在移走时记住原路径逐条还原，目前没做。
- **一次只处理一个文件夹、不递归子文件夹**：`zl_lie()` 只 listdir 一层，这是故意的 —— 递归删最容易出事。
- **只支持 Windows**：`SHFileOperationW` 是 Win32 API，非 Windows 上会直接说"这个功能只在 Windows 上能用"。
- **cmd 窗口要能拉起 Python**：子进程命令是 `sys.executable 小笨蛋.py --整理删除 …`；打成 exe 后会自动换成
  `小笨蛋.exe --整理删除 …`。万一被安全软件拦住起不来，会自动退回"主进程直接移"（功能不受影响，只是没有窗口看）。
- 桌面被 OneDrive 接管时按 `%OneDrive%\Desktop` 找；如果还有第三种重定向（组策略改到别的盘），会显示"文件夹不在"。

### 3. 识图四处修改

**（1）漏字（89 没识别出来）**：原因是检测框分数 0.45 上下，被默认的

新增 `_pai_hang()`：先按中心 y 分行（容差取该行字高的一半），行内按 x 从左到右。

**（3）领带被认成雨伞**：COCO 80 类里 tie 的权重占比极小，而"竖着的深色窄条"特征
上确实像收起的伞。新增 `_jiuzheng_lingdai()`，四条同时满足才改判（宁可少改）：
整个落在人框内（允许溢出人高的 6%）／高宽比 ≥ 1.35 且宽不到人宽 40%／
中轴贴着人身中线 25% 以内／整块平均亮度 < 140。实测那张正装照：`umbrella 0.9` → `tie`。

**（4）新增【穿搭】**：没有服装分类模型，所以只做"按部位取主色 → 翻成中文说法"，
判断不了的写"看不出"，不编品牌和款式。分区以**人脸**为尺子（下巴 + 脸高），
因为人框常常比人宽一圈、还往上多出一截，按百分比切躯干会切到下巴：

| 部位 | 位置（相对下巴 / 脸高） | 说明 |
| --- | --- | --- |
| 内搭 | +0.15~1.10 脸高 | 判"有没有大片白色像素"，不判颜色名（领带和脖子都在中间） |
| 上装 | +0.60~2.00 脸高，宽 ±1.55 脸宽 | 取主色时先剔除背景色和肤色 |
| 下装 | +2.10~3.40 脸高 | 人框被图片下边缘切断时写"下半身没入镜" |

实测输出：`黑外套，里面是白衬衫，系着黑领带，整体是正装/西装那一路；下半身没入镜。`

- 功能条、帮助、弹窗标题、提示语统一改成「壁纸」；内部 key 仍是 `beijing`，旧说法
  （"换背景""恢复背景"）继续认，新增"换壁纸/恢复壁纸"。
- 视频播放整条重写：**后台线程解码 + 缩放 + 压暗，界面每帧只贴图**。
  旧版是界面线程每 80~120ms 做两次全幅缩放 + 锐化 + 四次 PhotoImage，一帧 60~130ms，
  被硬压到 8~12fps —— 既慢又挡打字。

| 项目 | 改前 | 改后 |
| --- | --- | --- |
| 1440p 60fps 实际帧率 | 约 8~12 | 60.0（实测 3 秒 180 帧） |
| 4K 60fps 实际帧率 | 未跑满 | 58.6（实测 3 秒 176 帧） |
| 界面每帧成本 | 60~130 ms | 约 11 ms（只做 PhotoImage + 4 次 create_image） |
| 播放速度 | 慢放 | 原速（后台按墙钟对齐帧号，落后就 `grab()` 丢帧） |

缩放从 PIL 换成 `cv2.resize(INTER_AREA)` + `cv2.addWeighted`：同一帧
2560×1440 从 40~50ms 降到 5~8ms。界面刷新上限设在 33ms（约 30fps）——
实测 Tk 建一张整窗 PhotoImage 就要 11ms，跑到 50fps 会占半个核，打字立刻开始顿。

### 5.1 修「换了壁纸，按键还是上一张」（本轮追加）

**现象**：视频壁纸从 `fangyuan.mp4` 换成 `xiaobendan.mp4`，聊天区换了，但帮助/识图/
计算/壁纸/字体大小/打赏/清空聊天、发送、输入框上还是上一段视频的画面。

**根因**：玻璃控件的磨砂底不是"实时透明"，而是**从横条那张整窗背景图上裁一块
做高斯模糊**（Tk 没有 backdrop-filter，只能这么模拟）。这张图每帧都在换，但控件
只在悬停、改尺寸、换壁纸时才重画；切壁纸那次刷新又被"动态壁纸下不要分发空图"
的保护提前 return 掉了，于是按钮永远停在上一次重画时的那个画面。

**为什么不能"每帧全刷"**：8 个按钮 + 输入框 + 爱心全刷一遍实测 111~183ms，
30fps 下根本跑不动。

**为什么也不能换成"统一纯色"**：试过一版 —— 动态壁纸期间不取图、玻璃改走半透明
纯色。结果胶囊四角那块"铺底色"成了画面上一块明显的方底，椭圆雾化全丢了。
用户明确要求"一定要保持椭圆雾化透明按键，不能有矩形方边"，所以这条路作废。

**最终做法：轮播刷新。**
视频每来一帧，只重做**一个**控件的底图（实测 3~4ms，只换那张 image，不动文字
和光晕），10 个控件轮着转，一圈约 0.33 秒：

| 项目 | 数值 |
| --- | --- |
| 单个控件只换底图 | 3~4ms |
| 每帧额外开销 | 约 4ms（占 33ms 预算的 12%） |
| 每个控件的磨砂刷新周期 | 约 0.33 秒 |
| 开轮播后的视频帧率 | 27.6 fps（上限 30，实测 3 秒） |
| 切壁纸时全刷一次 | 111ms（一次性） |

因为胶囊四角取的就是**当前帧**那一块像素（不是平均色、更不是纯色），所以：
保持椭圆雾化、没有方边、不会挂着上一张壁纸。模糊过的画面每 0.33 秒更新一次，
肉眼看不出迟滞。

另外把磨砂缓存的键从 `id(_tu_pil)` 改成 `(_tu_xu, id)`：PIL 对象回收后内存地址
会被复用，光用 id 会把旧帧当成新帧，等于偶发"串帧"。

### 6. 流畅性

- 拖动/缩放窗口期间**不贴视频新帧**（`_zheng_suofang` 标志），省下的 11ms/帧 直接换成跟手感；
  松手后延迟补刷那一次再恢复。
- 大图先缩小再检测：`_suo_xiao()` 把长边超过 1600（OCR 是 2200）的图先缩，坐标再换算回去。
  实测那张 7898×5924 的 23MB 图：**识图总耗时 15.8 秒 → 1.8 秒**；
  手机原图的人脸检测 3083ms → 347ms。
- 连打 22 个字（视频正在播）实测每次按键 + 重绘 **1.8ms**。

## 本轮（第十一轮）的改动：识图两处故障

### 1. 人物和物体识别不出来 → OpenCV 读不了中文路径

**根因**：`cv2.dnn.readNet` / `cv2.FaceDetectorYN.create` 是 OpenCV 的 C++ 层直接开文件，**不认非 ASCII 路径**。而打包目录叫「小笨蛋」，正好是中文，所以三个模型全部加载失败，人物和物体都是 0 个。程序自己用 PIL 读图是认中文的，所以「选图不显示」和这个是两回事。

同一个模型文件在两个位置的表现（实测）：

| 路径 | 结果 |
| --- | --- |
| `C:\Users\study\Desktop\Ge\1\models\face_detection_yunet_2023mar.onnx` | `readNet 成功` |
| `C:\Users\study\Desktop\Pei\小笨蛋\models\...onnx` | `Can't read ONNX file`（Bad argument） |

**修法**：新增 `_yingwen_mogen(lu)` —— 路径是纯 ASCII 就原样返回，否则把模型复制到 `%LOCALAPPDATA%\XiaoBenDan\models\`（纯英文目录）再返回那条路径。三个模型统一走它，只付一次复制的代价。

> ⚠️ 走过的弯路：试过「把 onnx 读成 bytes 喂给 `cv2.dnn.readNet(字节)`」，结果**进程直接崩溃**（`exit=-1073741819`，访问违例）。OpenCV 5.0 的 dnn 不吃这个入口，此路不通，已全部撤掉。

### 2. 选文件后不显示图片 → `lu_lab` 变成了画布文字 id

`lu_lab` 在第九轮已经从 `tk.Label` 改成**画布上的文字 id（整数）**，但选图的 `zairu()` 里仍是 `self.lu_lab.config(text=...)`（原生控件 API）。抛 `AttributeError` 后，后面三行 —— 清空旧框、重绘图片、写状态栏 —— **全部被跳过**，所以图显示不出来。

**修法**：`self.ding.itemconfig(self.lu_lab, text=os.path.basename(lujing))`。

## 第十轮：缩放卡顿优化

单帧重绘从 **约 600 ms 降到 130~160 ms**（同一台机、同一脚本实测）。

| 项 | 改前 | 改后 |
| --- | --- | --- |
| 拖窗口一帧 | ~600 ms | 130~160 ms |
| `_ziti_shangxian()`（字号上限试算） | 660~790 ms | 37 ms（命中缓存 0.01 ms） |
| `_shua_niu_beijing()`（玻璃钮磨砂） | 165~200 ms | 91 ms，且拖动期间完全不跑 |

做法：
- **字号上限结果缓存**：键是 `(窗宽, 情绪, 字号, 功能项元组)`，改一项就重算。
- **不再每档新建字体对象**：`_ziti_wen_ben(size, weight)` 按尺寸缓存 `tkfont.Font`；46 档 × 2 个字体从「每次都建」变成「一次建完」。
- **整表缓存**：`_shangxian_kuan_biao()` 把每档的按钮宽、左右留白整表算好存起来，主循环只查表。
- **拖动期间降级磨砂**：`JingNiu._di_tu` 认出横条带 `_su_fang` 标记时走 1 倍采样、不做高斯模糊、不写缓存，松手后（`_yan_dai_shua`）再恢复精细。
- **防抖延时拉长**：`_chuang_kou_bian` → `after(200, ...)`，`LiaoTianQu._chicun_bian` → `after(180, ...)`。
  ⚠️ 这条是踩过坑的：防抖阈值必须**明显大于一帧耗时**，否则每帧都到点、每帧都跑一遍重活，比不做还慢（实测把 90 ms 防抖放进 100~600 ms 的帧里，帧耗时反弹到 578 ms）。
- **启动后预建字号表**：首屏之后 `after(800, _yu_re_ziti_biao)`，省掉用户第一次拖窗口那 192 ms。

### 1. 剩下的 130 ms 是什么（已查证，省不掉）
三个对照实验：
- 图元数量无关：48 / 440 / 904 个图元都是 53 ms。
- 整窗大图 vs 裁好的小块：44.7 ms vs 45.5 ms，没差别。
- 把三条横条贴图、对话区、玻璃钮全关掉：129 → 143 → 136 → 160 ms，**关掉反而更慢**。

结论：这 130 ms 是 Tk 重绘各控件窗口背景的固有成本，与业务代码无关。

## 已知限制

- **没有做成 .exe**：这台机器没装 PyInstaller，项目里也没有打包先例。要单文件 exe 需要先 `pip install pyinstaller`，再把 `rapidocr_onnxruntime` 和三个 onnx 模型一起打进去（约 300 MB+）。需要的话说一声。

### 三个必须写下来的坑

1. **子线程不能直接调 `root.after`。** 第一版就是这么写的，结果回复全部丢失：
   Tk 只在主线程正跑着 `mainloop()` 时才接受别的线程调 `after`，不在里面
   （比如测试时用 `update()` 轮询）就抛 `RuntimeError`，被 `except` 吞掉，
   表现是"发出去没回音、顶栏一直显示联网中"。改成 **队列 + 主线程每 80ms 取一次**，
   没有这个前提，也天然线程安全。

2. **失败别重试，直接认输。** 一开始"只要出错就去掉 thinking 重试一次"，
   结果 401（key 错）也重试，白等一轮，用户看到的是"一句 key 错误卡十几秒"。
   现在只有 `400 + 参数不认识` 才重试。

3. **关开关时要手动清"正在想…"标记。** 那条在飞请求已经作废，不会回来清标记，
   顶栏会永远停在「灵光中…」（已改为「灵光中…」并修好）。实测：发送 → 3 秒内关掉开关 → 顶栏立刻回到
   「（-__-） 平静」，慢回复回来后条数不变（被作废）。

### 天气为什么准了

原来那份 `素材五_天气.txt` 是**写死的假数据**（北京永远 18~26℃），这就是
"每次都不准"的原因。现在联网时改为：

1. `geocoding-api.open-meteo.com` 把城市名换成经纬度（结果缓存在内存，第二次起省 1 秒多）
2. `api.open-meteo.com` 取实况 + 当日高低温 + 降水概率
3. 拼成「【北京 天气】晴，现在 11℃，体感 8℃，湿度 60%，风 6 km/h，今天 4~16℃。」

实测输出：北京 3.6s（首次）/ 上海 2.9s / 乌鲁木齐 2.9s（表外的城市也能查）。

联网时天气判定比离线**放宽**了：原 `is_weather_question()` 要求"天气+疑问词"同时出现，
连「北京天气」都不认（那是给规则引擎用的，怕把"我心情跟天气一样"拉去报天气）。
联网走 `xiang_wen_tianqi()`：点城市名或带"几度/冷不冷/带伞/怎么样"才查，
「今天天气不错啊」不会被误判。

## 人设（第三轮·追加）

### 为什么要写人设

接上模型之后，如果不给设定，回答就是"DeepSeek 本人在说话"——
会分点、会总结、会说"作为一个AI"、会解释自己怎么工作。老师一眼就看出来。
所以 `REN_SHE` 从原来的 6 行扩成了完整人设（约 500 字，折成 token 约 400，成本可忽略）：

| 段 | 定的是什么 |
| --- | --- |
| 你是谁 | 一只住在电脑里的**灰猫**（和灰猫气泡、猫形窗口对得上），不是助手/程序 |
| 怎么说话 | 1~2 句、语气词、括号小动作、会改口、不列 1.2.3. |
| 脾气 | 好奇嘴碎、被夸会飘、被凶不记仇、难受时先陪着不讲道理 |
| 知道什么 | 知识和常识**正常答**；只有新闻/实时消息/电影书说不知道（避免瞎编） |
| 绝对不能说 | AI／语言模型／程序／提示词／系统／训练／模型／参数／接口／联网 |
| 当前状态 | 好感度、心情；<40 别太黏，100 恋人模式 |

### 一道硬闸：`_zi_bao()`

提示词是软的，聊久了模型还是会飘回助手腔。所以拿到回复后**再查一遍**：

```python
ZIPU_CI = ("作为一个", "我是AI", "我是人工智能", "我只是程序", "AI助手",
           "系统提示", "提示词", "训练数据", "我的模型", ...)
```

命中就带着「刚才那句不像你说的」重说一次；第二次还命中，直接岔开
（"你怎么老问这个呀，我还能是谁。"）。**宁可答得含糊，不能自曝。**

只盯第一人称自曝：用户问"你是不是AI"，她答"我不是AI"不会被拦（实测 `_zi_bao("我不是AI")` 返回空）。

### 实测（真实 key）

| 问 | 答 |
| --- | --- |
| 你是谁呀 | 我是小笨蛋呀，一只住在你电脑里的灰猫。（尾巴晃了晃）你一敲字我就凑过来了～ |

### 一个踩到的坑：过度装傻

第一版把"不知道"写得太宽，结果连"给我讲讲宇宙"都答"我说不上来"——
把装傻泛化到所有知识问题，功能白白变差。改成"知识正常答、只有实时消息/作品说不知道"
之后才正常。**人设是让它像猫，不是让它变笨。**

### 没做的两件事

- **长度截断**：本来想在代码里硬截到 3 句，放弃了 —— 用户让"讲个故事"时会被砍断，
  而且 `max_tokens=500` 已经卡了上限，实测回复都在 30~60 字。
- **记忆落盘**：只带最近 6 轮，问"上周那个"会断片。用户说后面再谈。

### 开关改成磨砂玻璃胶囊（第三轮·追加）

原来那颗纯色胶囊（开 #7a5f16 / 关 #33404f）放在壁纸上像贴了张色纸 ——
Tk 画布没有 alpha，半透明、磨砂、发光三样一个都做不出来，只能画纯色。

现在改成 `_lianwang_tu()` 用 PIL 合成一张 RGBA 图再贴到画布上：

| 层 | 做法 |
| --- | --- |
| 玻璃底 | 从 `ding._tu_pil` 裁身后那块 → `GaussianBlur(5)` → 与深色 blend 0.42 |
| 圆角 | 圆角矩形 mask 做遮罩（半径 = 高的一半，标准胶囊） |
| 顶部高光 | 竖向渐变白，最亮 48/255，模拟玻璃厚度 |
| 霓虹 | 宽 7 的金色线先高斯模糊当辉光，再压一条 2px 亮芯；关状态换冷蓝 |
| 白边 | 一圈 26% 白的 1px 内描边 |
| 滑块 | 半透明白 216 + 偏左上高光；开在右、关在左 |
| 文字 | 白字 + 1px 深色投影（亮壁纸上也读得清） |

**按 3 倍尺寸画再 LANCZOS 缩回去**：80×28 直接画，滑块和两端圆弧会有锯齿，
缩小看像多边形。

实测：合成一张 **1.2ms**，整体重画（含 PhotoImage + 贴图）**2.9ms**，
只在"换壁纸 / 切状态 / 尺寸变"时算，**有缓存**（key = 背景对象 id + 状态 + 尺寸）。
打字回归 1.1ms/键，点击命中正常（image + 两个 text 都在 `lianwang` tag 上）。

现在统一走 `_nei_chuang(宽, 高, 名字)`：在主窗口里 `place(relx=0.5, rely=0.5)`
贴一块 Frame，看起来是"程序里长出来的一块"，跟着窗口移动缩放，不会跑到窗口外。

- 传 0,0 表示按内容自适应尺寸（字体面板、清空确认用这个）；
- 打开新的会自动关掉旧的（`_guan_nei()`），天然互斥；
- 顺手删掉了 `grab_set` / `grab_release` / `title` / `geometry` / `transient`
  —— Frame 上没有这些方法（删 `grab_release` 时掏空了 try 块，靠脚本补了 `pass`）。

**副作用**：内嵌面板没有模态抓取，面板后面的按钮理论上还能点到。

会把壁纸全盖住，所以暂时不做。

## 第十八轮：灵光等待期的"正在思考ing……"

### 问题
灵光要走网络，几十毫秒到几秒都有可能。这段时间对话区完全没动静，
用户看到的是"发出去一条消息，然后界面卡住了"。

### 做法
发出消息 → 立刻在对话区摆一条占位 → 回复到了**原地改写**成正式内容。

```
用户：外面是不是有点冷
小笨蛋：（手指无意识地摩挲着戒指）正在思考ing……      ← 立刻出现
        ↓ 1~3 秒后原地变成
小笨蛋：（把脸从兜帽里露出来）风有点凉了……你冷不冷？
```

| 位置 | 改动 |
| --- | --- |
| `Duihua.tian_zhan()` | 追加一条占位并返回**这一条对象本身** |
| `Duihua.gai_tiao()` | 按对象原地改写（不按下标） |
| `Duihua.shan_tiao()` | 按对象删除（占位没等来回复时用） |
| `_fasong_zaiwang()` | 起线程前先摆占位，登记到 `_lw_zhan[xu]` |
| `_lw_dao()` | 成功→改写；失败→撤占位再走本地；过期→撤占位 |

### 关键设计：为什么按对象而不是按下标

`self._tiao` 原来存的是元组，改成 **list**（可变），占位那条直接返回引用。

按下标改会踩这个坑：连发两句时，第一句的占位被撤掉后，后面所有下标往前挪一位，
第二句的占位就改到别人身上了。拿对象本身去改/删，下标怎么漂都不影响。

`for kind, wenben, biaoti in self._tiao` 对 list 照样解包，绘制代码一行没改。

### 三种结局都测了

| 情况 | 结果 |
| --- | --- |
| 正常返回 | 占位原地变成回复，占位残留 0 |
| 连发两句 | 第一句占位撤销、第二句占位变回复，占位残留 0 |
| API 失败 | 占位撤销 → 「（灵光断了）」→ 本地规则回答，占位残留 0 |

## 第十九轮：语音播报（晓伊音色）

### 需求
1. 用温柔的真人声念她说的话
2. **动作描写一律不念** —— 正常对话没人会把"把脸埋进兜帽里"说出来
3. 短句补停顿 / 环境音（能做就做，做不出来就算）
4. 顶栏加 🔊 / 🔇，点一下切换

### 技术选型

| 方案 | 音质 | 体积 | 结论 |
| --- | --- | --- | --- |
| 系统 SAPI（慧慧） | 机械音 | 0 | ❌ 用户听过后否掉 |
| **edge-tts（晓伊）** | **真人级** | +2 MB | ✅ 采用 |
| 本地神经 TTS | 可克隆 | +GB | 太重 |

- 音色 `zh-CN-XiaoyiNeural`（晓伊），语速 `-12%`
- 播 mp3 用 **Windows 自带 MCI**（winmm），不额外装 playsound/pydub

### 文本清洗（关键）

```
（拉了拉深色的兜帽，脸颊微红）你来了……小笨蛋今天也在这里等你哦。
                ↓  tts_qingli()
你来了……小笨蛋今天也在这里等你哦          ← 动作全剥掉
```

去掉：中文括号 `（）`、英文括号 `()`、方括号 `[]`、书名号 `【】`、颜文字残渣、图标字符、连续标点。
只念正文，不念旁白（`xie_ru_pangbai` 那一层是文字装饰）。

### 停顿方案：SSML 走不通，改用标点

本来想用 `<break time='350ms'/>` 加停顿，实测发现：

> edge-tts 会把整段文本先 `escape()` 再拼 SSML，`<break>` 被转义成字面字符，
> **引擎把它当文字念了出来** —— 同一句从 3.2 秒变成 5.9 秒，多出来的就是 "break time 350ms"。

实测各标点的天然停顿：

| 写法 | 时长 |
| --- | --- |
| 句号 | 3216 ms |
| 逗号 | 2904 ms |
| 省略号 | 2952 ms |
| 双逗号 | 2904 ms |

句号已经最长，堆标点反而更短。所以**不加 SSML，停顿交给标点自己**。

### 顶栏 🔊 / 🔇

不用 emoji（Tk 8.6 部分 Windows 上非 BMP 字符会变方块），自己用 Canvas 画：
三角喇叭 + 两道声波 / 红色斜杠。开着是金底金字，关着是灰底红斜杠。

- 默认**关**，状态存 `语音开关.txt`
- 关掉时立刻停掉正在念的那句
- 打开时先念最近一句，让用户当场听到效果

### 播放调度

```
回复落地 → bo_bao() → 后台线程合成（0.5~2s） → 主线程 MCI 播放
                     ↘ 同一句话第二次直接读 语音缓存/xxx.mp3
```

- **必须开线程**：edge-tts 要联网，主线程等就会卡界面
- **新句打断旧句**：语音排队会越拖越远，最后和文字完全对不上
- **断网静默**：合成失败只打印到控制台，不弹框、不影响文字

## 第二十轮：离线答非所问（大幅修）

### 三个根因

| 现象 | 根因 |
| --- | --- |
| 灵光回答偏「说自己」 | 人设写「反应慢半拍」，模型据此真的装傻（已修） |
| 灵光讲笑话不完整 | 「极度安静/社恐」压掉主动性（已修） |
| 离线答非所问 | **上层抢话**：话题表、定义层、工具层互相抢，抢到就念，不看问的是什么 |

### 关键认识：不是"答得不好"，是"答的不是这件事"

同一个问句会被四五个层依次尝试，谁先命中谁说话。命中的层往往只对上**一个词**，
于是就出现了这些：

## 第二十一轮：人设重写（去 AI 味 + 人物饱满）

### 为什么原来那股 AI 味去不掉

旧人设是一套**规则清单**：

```
【回答原则】【怎么说话】【害羞的分寸】【脾气】【知道什么】【绝对不能说】
1. … 2. … 3. …
```

模型看到的是 "1. 用户问什么就先答这件事；2. 只有明确问…；3. 人设只决定…"，
它输出的就是**面面俱到、三段式、结尾必带反问**的文字 —— 那是规则的形状，不是人的形状。

光写"不要用首先其次"没用。**得给它对照**：左边是她绝不会说的，右边才是她。

### 新写法：人物档案，不是规则

| 旧 | 新 |
| --- | --- |
| 【你是谁】| 【长什么样】【家】【几件把她变成现在这样的事】|
| 【回答原则】+ 编号 | 叙述句：「问她什么，就先答这件事。问数学难不难就聊数学哪里难」|
| 【怎么说话】规则 | 「她说话像打字：想到哪说到哪，句子短」+ **五组对照例句** |
| 抽象描述 | 具体细节：发尾自己剪的、项圈自己攒钱买的、戒指太大用红绳缠了两圈 |

### 补的东西

**长相**：银灰色短发（自己染花了不管）、浅灰偏蓝的眼睛、眼尾往下显得没睡醒、
左眼下有颗小痣、一米五八、手腕细、冬天手凉会缩袖子。
兜帽常扣着——不是神秘，是初三把头发剪坏了，从此习惯。

**家庭**：江南小县城。父亲开修表配钥匙的铺子，玻璃柜台后面摊着拆开的机芯，
放大镜用黑皮筋绑头上；母亲超市理货，手上都是纸箱子的味道；弟弟念初二。

**关键设计：她的"慢"是有出处的。**
小时候在铺子里写作业，满墙的钟一起走，滴答，一格一格 —— 所以她对"慢"不着急。
**慢不是笨，是从小在钟表堆里养出来的节奏。**

**把她变成现在这样的几件事**：三年级被老师说"说话大声点"站那半天没出声、
高中在图书馆整理书架两年、老公园长廊那个总在下棋的老爷爷后来位置空了。

**时间线钉死**：十九岁，高中毕业两年，没上大学也没复读，图书馆干了两年去年底被外包换掉，
现在白天在爸铺子看店。**不是学生，没有课、没有暑假、没有作业。**

### 去 AI 味的核心：五组对照

```
她说不出：「这个问题其实可以分三个层面来看，首先是……」
她会说：  「我想不太明白。是不是跟……那个有关？」

她说不出：「是的，我理解你的感受。生活总有起伏，重要的是保持心态。」
```

> 括号里的小动作，**能不写就不写**。大多数回复里一个都没有才对。

## 第二十三轮：功能面板不再置顶

### 问题

用户原话：

> "整理助手"窗口的权限太高了，弹出的 cmd、回收站都被它盖住了
> 不要置顶最高

`GongNengYe` 建窗口时写的是：

```python
self.win.overrideredirect(True)
self.win.attributes("-topmost", True)     # ← 元凶
```

`-topmost` 是 `WS_EX_TOPMOST`，效果是**压在所有窗口上面**，包括别的程序。
整理助手的执行流程里有两次会弹系统窗口：

- 「移到回收站」时 `subprocess.Popen(..., CREATE_NEW_CONSOLE)` 起一个 cmd 显示进度
- 「打开回收站」时 `ShellExecuteW("shell:RecycleBinFolder")`

这两个都在面板底下，用户从头到尾看不到，等于白弹。

### 改法

```python
self.win.attributes("-topmost", False)    # 普通层，谁都能盖
self.win.transient(self.root)             # 但又永远压在主窗口上
```

`transient` 是关键：加它之后窗口变成主窗口的 **owned window**。
Windows 的规则是 owner 窗口永远在 owned 窗口下面 —— 所以：

- 点主窗口 → 面板不会沉下去（transient 保证）
- 别的程序（cmd、回收站、资源管理器）→ 能正常盖住面板（不再是 topmost）

两个都要，缺一个就出问题：
- 只去掉 topmost 不加 transient → 点一下主窗口，面板就跑到后面去了，看着像关了
- 只加 transient 不去 topmost → 还是一个压住 cmd 的流氓窗口

### 验证方式

不能只查 style 位，得看**那个像素上到底是谁**。用 `WindowFromPoint` + 截屏采色：

| 检查项 | 结果 |
| --- | --- |
| 面板 `WS_EX_TOPMOST` 位 | `False` ✓ |
| 面板中心像素 = 深色玻璃 (26,32,41) | 面板画在主窗口之上 ✓ |
| 压一个窗口模拟 cmd → 中心像素变绿 (0,170,0) | **外部窗口能盖住面板** ✓ |
| 主窗口 `lift()` / `SetForegroundWindow` 后 | 面板仍在上 ✓ |
| 切页 zhengli / xiezuo / guanyu | 都正常显示 ✓ |
| 关闭 → 重新打开 | 新面板 TOPMOST 仍为 False ✓ |

（中途踩了个坑：一开始用 `GetTopWindow` 枚举 Z 序，结果 `overrideredirect` 的
Toplevel 在 Tk 里是独立顶层，枚举出来的顺序和视觉前后对不上，得出"面板在下"的
错误结论。改用 `WindowFromPoint` 直接问"这个坐标上是谁"+截屏采色才靠得住。）

事件队列堆起来，Tk 根本轮不到处理点击。

### 五处改动

**① 面板底图压暗挪到 1/3 小图上做，放大用 BILINEAR**

```python
# 原来：小图模糊 → BICUBIC 放大到全尺寸(3.16ms) → 全尺寸 blend(2.04ms)
# 现在：小图模糊 → 小图 blend(0.25ms) → BILINEAR 放大(1.6ms)
xiao = Image.blend(xiao, self._hei_xiao, an)
di = xiao.resize((kuan, gao), Image.BILINEAR)
```

blend 是逐像素线性混合，先混后放大和先放大后混肉眼看不出差别（本来就糊）。
**10.1ms → 6.7ms**。

**② 面板底图节拍 90ms → 160ms**

底图是**重度模糊**的，11fps 和 6fps 肉眼看不出。
**16.9% → 8.0%**。

**③ `_hua_beijing` 图元复用**

原来每帧 `delete("beijing")` + `create_image` + `tag_lower`（4.83ms）。
改成建一次、之后只 `itemconfigure` + `coords`。图元被别处清掉时 `self.type()` 会抛，
那时才重建 —— 不会出现"背景凭空消失"。

还发现一个 bug：`_dong_tai_kai` 里还有一句 `self.delete("beijing")`，
把刚缓存的图元删了，**图元复用等于白做**。一并去掉。

**④ 磨砂轮刷从每帧改成每 3 帧**

`_lun_liu_shua` 每帧刷一个玻璃钮的磨砂底（8.34ms/帧 = 22.8%）。
10 个控件轮一圈从 0.3s 变成 0.9s —— 模糊过的按钮底，看不出迟滞。
**22.8% → 4.9%**。

**⑤ 三条横条的图元也复用**

`BoLiTiao._hua()` 同样每帧 delete+create，和 ③ 是一模一样的问题，之前漏了。

### 换壁纸"秒切"

**原来的问题**：换完视频壁纸要 **514ms** 才出新画面。

2. 首帧 `read()`（4K 解码）：72~153ms
3. 后台线程按墙钟对齐 + 界面等下一次 tick：其余几百毫秒

这期间界面上还是上一张壁纸（`_quan_pil` 没换）。
面板更惨 —— 它读的就是 `_quan_pil`，于是先挂着旧画面。

**改法**：`DongTaiBeiJing.__init__` 里同步读掉首帧存成 `_shou`。

```python
# __init__ 里
_ok, _shou = cap.read()
self._shou = _shou if _ok else None

# qu_zui_xin 里
if self._quan is None and self._shou is not None:
    _quan = self._suo_fang(self._shou, _kuan, _gao, _tou)
    self._quan = _quan; self._xu += 1; self._shou = None
```

| xiaobendan.mp4 | ~400 ms | **106 ms** |
| naiwa.jpg (静态) | ~100 ms | **74 ms** |

### "面板先糊一段、再点一次才切"

**踩到的坑**：第一次写成了 `getattr(self.winfo_toplevel(), "_gongneng_ye", None)` ——
`winfo_toplevel()` 返的是 Tk 的 root，而 `_gongneng_ye` 挂在 `DuihuaChuangkou` 实例上，

```
+200 ms  (22,25,24)
```

## 第二十五轮：换壁纸秒切 + 面板一次打开不卡

### 三个症状，四个根因

| 症状 | 根因 |
| --- | --- |
| 换新视频壁纸"不秒切" | ① 换壁纸那段 150~250ms 全压在调用线程里，屏幕在此期间冻结在旧画面 |
| 面板首次打开先显示旧背景，再点一次才换 | ② 面板创建时先按"默认深色底 + 暖金"画一遍，等第一次 `_dong_tai` 发现壁纸变了，**再把整页重画第二遍** |
| 之后点面板卡，点两次甚至打不开 | ③ `_gongneng_kaile` 在造窗口**之前**就置 True，构造中途抛异常时不还原 → 主窗口从此不贴壁纸，且每次都在同一处失败 |
| 同上 | ④ 旧面板引用失效时只把 `_gongneng_ye` 置空，没有 `destroy` → 上面挂的 160ms 定时器链成了僵尸，每失败一次多一条 |

### 实测（优化前 → 优化后）

| 指标 | 前 | 后 |
| --- | --- | --- |
| 点「☰ 功能」到面板出现（4K 视频在播） | 150~181 ms | **103~112 ms** |
| `GongNengYe.__init__` 本体 | 114~132 ms | **70~77 ms** |
| 其中整页 `_hui` 次数 | 2 次（60ms） | **1 次（25ms）** |
| 其中 `_zuo_guang` 光斑 | 22 ms（每次都重算） | **0 ms（缓存）** |
| 换视频壁纸调用阻塞 | 187~246 ms | **131~172 ms** |
| 换壁纸后画面变新 | 400~514 ms | **173~222 ms** |

### 改法一：面板一次成型，不再画两遍

原来 `__init__` 是这样的顺序：

```python
self._bj_lu = "\x00"                    # 假装不知道壁纸
self.se, ... = self._jin_se()           # 先给暖金
self.di = self._zuo_di()                # 先按默认深色渐变建底图
...
self._hui(dan=False)                    # 第 1 遍整页
self._dong_tai()                        # 发现壁纸路径变了
    → _huan_se() → _hui()               # 第 2 遍整页
    → _zuo_di(yuan)                     # 第 2 遍底图
```

现在开头就把壁纸接过来，颜色、底图、内容层各只算一次：

```python
_yuan0 = self._bi_jing()
self._bj_lu = d._bj_lujing or "\x00"
self.se, ... = self._qu_se(_yuan0)      # 一次算对
self.di = self._zuo_di(_yuan0)          # 一次建对
self._di_jiu_tu = _yuan0                # 记住这张，别让 _dong_tai 再建
```

**`_dong_tai` 里那颗"视频就每拍重建底图"的雷**：条件原来是

```python
if yuan is not None and (dong is not None or id(yuan) != self._di_jiu):
```

只要视频在播就无条件重建。于是 `__init__` 刚建完，紧接着这一次 `_dong_tai`
拿**同一帧**又建了一遍（14ms，白烧）。改成按**图对象身份**判断并留住引用：

```python
if yuan is not None and yuan is not self._di_jiu_tu:
```

同一个对象像素完全一样，重建没有意义。视频每来新帧对象就换，照旧每拍更新。

### 改法二：鼠标光斑缓存

`_zuo_guang()` 是 192×192 的**逐像素** `putpixel` 循环（36864 次），实测 22ms。
而它和面板尺寸无关、内容永远一样 —— 每次开面板重算纯属浪费。
加模块级 `_GN_GUANG_CUN`，按半径存一份，第二次起 0ms。

### 改法三：标志后置 + 失败回滚（这是"打不开"的真凶）

```python
# 原来：造窗口之前就写
self.zhu.duihua._gongneng_kaile = True
self.win = tk.Toplevel(...)
```

构造中途任何一步抛异常，`dakai_gongnengye` 会把 `_gongneng_ye` 置空走兜底，
**但这个标志留在 True 上**。后果：

- 主窗口 `_dong_tai_kai` 一直认为"面板盖着"，从此不再贴壁纸 → 换什么壁纸都"不生效"
- 每次再点都在同一处炸 → "打不开"

改成构造**末尾**再置位，并在 `dakai_gongnengye` 的 except 里回滚两个标志。

### 改法四：旧面板引用失效时要真的收掉

```python
try:
    ye.win.lift(); return
except Exception:
    ye.guan()          # ← 原来是 self._gongneng_ye = None
    self._gongneng_ye = None
```

只置空的话，那个对象上 `self.win.after(160, self._dong_tai)` 的链还在跑，
而且它每 160ms 做一次整图重建 —— 每失败一次多一条，越点越卡。

### 改法五：一次点击就到最前

`overrideredirect` 的窗口创建后不一定自动跑到最前，主窗口又刚被点过。
创建完补一次：

```python
self.win.lift()
self.win.attributes("-topmost", True)
self.win.attributes("-topmost", False)   # 立刻撤掉，绝不留常驻置顶
```

实测后再查 `WS_EX_TOPMOST`：`False` —— 上一轮"不许压住 cmd / 回收站"的要求没被破坏。

### 改法六：关掉面板立刻补一帧

面板盖着的整段时间主窗口是不贴壁纸的（省 CPU）。关掉那一瞬间什么都没做，
露出来的还是"开面板之前"那张 —— 要等下一拍 33ms；视频线程若已停下就**永远不补**，
于是"再点一次功能面板才切到新壁纸"。

`guan()` 里补一次：拿手上最新的整窗帧直接贴。

```python
jian = ImageTk.PhotoImage(tu)
d._quan_tu = jian
d._hua_beijing(tu.width, tu.height)
d._dong_tai_zhen(jian, tu, tu.width, tu.height)
```

（静态壁纸走 `_shua_quan_beijing()`，路径不同。）

### 验证

```
① 面板开着换壁纸 → 面板底图 (51,57,50)，新帧 (68,80,71)   立刻正确
② 面板关掉 → 主窗 (72,82,75) ≈ 新壁纸                     无需等节拍
③ 一次点击面板就在触点最上                                 3/3 通过
④ 模拟 _hui 抛异常：_gongneng_kaile=False，主窗照常贴壁纸    ✓
⑤ 连开连关 8 次：每秒 _dong_tai 稳定 4 次，不随次数增长      ✓
⑥ 置顶位：exstyle 无 WS_EX_TOPMOST                         ✓
⑦ 10 个页面 / 整理助手扫描 / 新建文本 / 静态壁纸 / 聊天      全通过
```

### 还剩一点

换 4K 视频仍有约 130~170ms 的**同步**开销，来自 `cv2.VideoCapture` 打开（约 40ms）
+ 首帧解码（4K 约 100ms）。这部分不挪到后台线程就省不掉 ——
而挪走会让"这个视频放不了"这类报错没法在调用处同步告诉用户，属于行为改变，
这轮没动。首帧解码放在换壁纸那一刻，已经是"能立刻看到新画面"的最短路径。

## 第二十六轮：对比新旧版本，修"换壁纸不生效 / 面板要开两次"

### 对照对象

- **旧版**：`小笨蛋.zip` 里的 `源代码/小笨蛋.py`（2026-11-04 13:42，15038 行）
- **新版**：当前（含语音、人设、整理助手抽屉等）

把两边同名方法逐个抽出来做 unified diff，壁纸/面板相关一共 16 个方法。

### 两版真正的差异（只列相关的）

| 方法 | 旧 | 新 | 影响 |
| --- | --- | --- | --- |
| `GongNengYe.__init__` | `-topmost True` | `False` + `transient(root)` + 抬前脉冲 | 层级 |
| `GongNengYe.__init__` | 先暖金/默认底再重画 | 一次成型 | 开面板耗时 |
| `GongNengYe._dong_tai` | 90ms，流光每 2 拍 | 160ms，流光每拍 | 面板底图帧率 |
| `DuihuaChuangkou._lun_liu_shua` | 每帧 | 每 3 帧 | CPU |
| `LiaoTianQu._dong_tai_kai` | 有 `delete("beijing")` | 去掉了 | 修图元复用 |
| `LiaoTianQu.she_beijing` | 只换图 | 多了 `shua_di_xian_zai()` | 面板立刻刷 |
| `GongNengYe.guan` | 只清标志 | 立刻补一帧 | 关面板不闪旧图 |

**结论：`_gongneng_kaile` 那段"省 CPU 的跳过"两版一模一样，所以"面板里新、窗外旧"不是新加的回归，是一直都在的老毛病** —— 只是新版面板换成实时毛玻璃之后，面板内部和窗外那圈边的色差被放大了，才被看出来。

### 真正的根因

```python
# LiaoTianQu._dong_tai_kai（旧、新都一样）
if getattr(self, "_gongneng_kaile", False):
    # 功能页盖着整窗，这时给三条横条贴图是白烧 CPU
    pass                      # ← 一帧都不贴
```

注释写的是"功能页盖着整窗"，**但面板根本盖不住整窗**：

```
窗口 1160×800
面板 min(1000, 1160-32) × min(780, 800-32) = 1000×768
x0 = (1160-1000)//2 = 80        → 左右各露 80px
y0 = (800-768)//2  = 16         → 上下各露 16px
```

于是：面板里已经是新壁纸（它自己读 `_quan_pil`），窗外那圈边还挂着旧壁纸，
关掉面板 `_gongneng_kaile` 变 False 才补上 —— 就是"关掉面板后才切到新壁纸"。

实测（面板开着换壁纸，采样窗外那条缝）：

```
换壁纸前： 左缝 (43,44,29)
+0/100/300/800ms： 左缝 (43,44,29)      ← 一帧没动
关掉面板： 左缝 (83,97,85)              ← 这时才变
```

### 改法

**① 面板开着不再整体跳过**，改成"分级降频"：

| 层 | 面板关 | 面板开 |
| --- | --- | --- |
| 对话区 `_hua_beijing` | 每帧 | **每帧**（图元复用，0.1ms） |
| 三条横条 `_dong_tai_hui` | 每帧 | **每 3 帧**（10fps，那么窄的边看不出） |
| 玻璃钮磨砂 `_lun_liu_shua` | 轮刷 | **仍不开**（这才是真费 CPU 的） |

换壁纸时把计数归零，让**第一帧**就走"每 3 帧里的第 1 帧"，
不用等最多 2 拍（66ms）。

改后同一测法：

```
+100ms 左缝 (42,50,46)
+300ms 左缝 (40,51,47)
+800ms 左缝 (69,82,73)      ← 跟着视频在动
```

**② 面板抬到最前改成 map 之后再抬**

```python
self.win.after_idle(self._tai_dao_qian)   # 原来是紧接着 lift()
```

`overrideredirect` 的窗口在 `__init__` 那一刻还没 map，直接 `lift()` 是空操作。
排到 `after_idle`（本轮事件处理完、窗口已显示）再抬，一次点击就在最前。
抬法仍是 `lift()` + topmost 脉冲，**用完立刻撤**，`WS_EX_TOPMOST` 复查为 `False`。

**③ 二次点击也走同一套抬法**

`dakai_gongnengye` 里"面板已存在"那一支原来只 `lift()`，
面板被别的程序盖着时抬不出自己的层级，现在调同一个 `_tai_dao_qian()`。

**④ 标志自愈**

```python
def _gongneng_zhanshi(self):
    kaile = bool(getattr(self, "_gongneng_kaile", False))
    if kaile and getattr(self, "_gongneng_ye_ref", None) is None:
        self._gongneng_kaile = False     # 面板没了，别让标志把壁纸锁死
        kaile = False
    return kaile
```

`_gongneng_kaile` 一旦因为异常残留在 True，主窗口就再也不刷壁纸 ——
换什么壁纸都"不生效"，看着像卡死。现在每取一帧都核对一次。

## 第二十七轮：快速连点两张视频壁纸会崩（access violation）

### 现象

连点两张视频壁纸，进程直接消失：Windows 弹 **"python has stopped working"**，
控制台没有 traceback，只停在 Pillow 的两条 DeprecationWarning 上。

### 抓到的现场（faulthandler 多线程栈）

```
Thread 0x00005140 [Thread-26 (_xun_huan)]: Windows fatal exception: access violation
  File "小笨蛋.py", line 5657 in _xun_huan        ← ok, zhen = self.cap.read()
  File "threading.py", line 1024 in run

Thread 0x0000b9a4（主线程）
  File "小笨蛋.py", line 5610 in guan             ← self.cap.release()
  File "小笨蛋.py", line 6807 in _ting_dongtai
  File "小笨蛋.py", line 6724 in she_beijing
```

**同一时刻，两个线程在同一个 `cv2.VideoCapture` 上：一个 `read()`，一个 `release()`。**

### 为什么会崩成这样

`cv2.VideoCapture` 底层是 FFmpeg 的解码器上下文（一块裸内存，一堆裸指针）。
`release()` 会把它整块 free 掉。如果此刻另一个线程正在 `read()` 里用那些指针解码，
下一次访问就是**野指针** —— Windows 直接把进程杀掉（0xC0000005）。

Python 这层什么都拦不住：不是 raise，是段错误，所以**一条 traceback 都没有**，
只剩崩溃前打印的两条 Pillow 警告，看着像"警告把它搞崩了"，其实毫无关系
（`getdata` 是 Pillow 14 的弃用提醒，跟这个崩溃无关）。

原来 `guan()` 就是这么写的：

```python
def guan(self):
    self._ting = True
    if self.cap is not None:
        self.cap.release()      # ← 主线程直接放，不管后台线程在不在读
```

平时切一张、中间隔几百毫秒，后台线程多半正好在 `sleep(≤0.2)`，碰不上；
**手快连点**时两次切换只隔几十毫秒，后台线程十有八九正卡在 `read()` 里，必崩。

### 改法

**① 加一把专门保护"句柄"的锁**

```python
self._cap_suo = threading.Lock()
```

后台线程每一次 `read()` / `grab()` / `set()` / GIF 的 `seek()` 都先拿这把锁，
**拿到之后再确认一次 `_ting`**：

```python
with self._cap_suo:
    if self._ting:
        break
    ok, zhen = self.cap.read()
```

**② `guan()` 不再"想放就放"，只抢一次锁**

```python
def guan(self):
    self._ting = True
    if self._cap_suo.acquire(blocking=False):
        try:
            self._fang_shou()        # 抢到了 ⇒ 线程此刻没在读，可以放
        finally:
            self._cap_suo.release()
    # 抢不到 ⇒ 线程正在 read() 里，放过它，让它退出前自己放
```

**③ 线程退出前自己释放句柄**（这才是有序的那条路）

```python
# while 循环结束后
with self._cap_suo:
    self._fang_shou()
```

这样"谁在用谁负责放"，主线程永远不会在别人读的时候去 free。

### 为什么不是简单加个 `time.sleep`

睡眠只是把概率压低，5ms 的窗口和 50ms 的窗口一样会撞上，只是撞得少。
必须让"读"和"放"互斥，才谈得上不崩。

### 验证

| 场景 | 结果 |
| --- | --- |
| 间隔 100ms 切 40 次 | 通过（改前第 1 次就崩） |
| 间隔 25ms 切 60 次 | 通过，10.1s，线程数始终 1 |
| 不留间隔连点 30 次 | 通过 |
| 视频播放 | 2 秒 41 帧，正常 |
| 视频 → 静态 → 视频 | 正常，`_bj_dong` 正确置空/重建 |
| GIF（8 帧） | 正常，2 秒 17 帧 |

| 面板 10 页 / 整理扫描 / 新建文本 / 聊天 | 全通过 |

线程数在 60 次连切之后仍然是 1 —— 说明每个解码线程都正常退出并释放了句柄，
没有句柄泄漏。

2. `_gongneng_kaile` 现在**不是"全停"**，是"三条横条降频到每 3 帧"。
   它的含义是"面板开着、磨砂轮刷可以不刷"，不是"主窗不用画"——
   面板盖不住整窗，窗边那圈是看得见的（第二十六轮）。
3. `DongTaiBeiJing` 里 **`cap` 的读和放必须互斥**（`_cap_suo`）。
   主线程只能在 `acquire(blocking=False)` 抢到锁时才 `release()`，
   否则就是第二十七轮那个"闪退却没有 traceback"。
4. 功能面板**不要加常驻 `-topmost`**：整理助手弹的 cmd、系统回收站必须能盖住它。
5. 界面上任何"从 x 画到 you"的文字，用 `_gn_jie()` 按**像素**截断，别按字数截。
6. **功能排在人设前面**。天气是唯一的例外条款：人设里写着"她看不到外面"，但问天气时
   必须照接口数据答（灵光模式靠 `TQ_WEATHER_RULE` 追加在 system 后面，且答完要用
   `_tq_shuo_dui()` 校验城市和数字，不过关就退回接口原文）。别再往人设里加"能报天气"
   之类的句子，会跟"不知道外面的新闻"打架。
7. **删文件只有一个出口**：`zl_weixian()` 判定 + `_zl_song_huishouzhan()` 执行。
   白名单现在只有「演示夹」；「指定删除」靠 `mingque=True` 放行用户亲手点的文件
   （子进程那条路靠清单里的 `D|` 前缀传递这个语义）。新增任何"删"的入口，
   必须走这两个函数，别自己调 SHFileOperation。
8. **功能页不是"贴在屏幕上的玻璃"**：它是主窗的 owned window（`transient` + 不常驻
   `-topmost`），位置靠 `GongNengYe._gen_sui()` 跟着主窗 `<Configure>` 走，
   层级靠主窗 `<FocusIn>` 时 `lift()` 压回主窗上面。这样别的程序（资源管理器、
   回收站、整理助手的 cmd）一激活照样能盖住它 —— 别再给它加常驻 `-topmost`。

## 8. 天气这条链怎么走（第二十八轮重写）

```
用户一句话
  ↓ is_weather_question() / _tq_genjin()          ← 追问「那明天呢」靠 _TQ_SHANG 记的上一座城
  ↓ _zhao_chengshi()   城市：常见城名表 → 正则抠「XX天气」 → 上一次问过的城 → 配置里的默认城市
  ↓ _tq_fanwei()       日期：now / day(明天,后天) / days(未来7天) / weekend
  ↓ _tq_qu()           坐标 + 当前 + 逐日（Open-Meteo，同城 10 分钟缓存）
  ↓ _tq_shuo()         拼人话：数字只用接口给的
  ↓ 离线：_fasong_tianqi() 子线程 → _tq_hui 队列 → _tq_dao() 原地换掉"正在调用天气……"
     灵光：数据塞进 prompt + TQ_WEATHER_RULE → 模型说人话 → _tq_shuo_dui() 校验 → 不过关退回原文
```

**地名解析为什么三级兜底**：Open-Meteo 的地理编码只认拉丁字母 —— 北京上海南京能查到，
扬州宿迁查不到；更要命的是中文名会撞同名小村子（"东京"命中江苏一个村）。
所以：①Open-Meteo（中文名要求人口 ≥10 万且名字对得上）→ ②国外城市换英文名再查一次
（`TQ_WAI_ALIAS`）→ ③wttr.in（**只接受落在中国的结果**，否则它会拿自己服务器所在的
伦敦顶包，实测"阿斯嘉特"被解析成伦敦 Strand）→ ④都不行就说"没查到"，
**绝不拿默认城市顶替**。

## 9. 语音播报这条链怎么走（第二十九轮重写）

```
xie_ru_ta() / bo_bao() 被调用
  ↓ tts_qieduan()      按 。！？； 切段，>30 字再按逗号切，最多 5 段（一个字都不丢）
  ↓ 线程 A：tts_hecheng(段, qingxu=当前情绪)  → 队列
     线程 B：tts_bofang(mp3) → tts_deng(等播完) → tts_ting(关别名) → 取下一段
  ↓ tts_hecheng 里：TTS_QINGXU[情绪] → (rate, pitch) → 缓存键带上这两个参数
```

**为什么快**：`c.save()` 要等整段音频下载完才返回（一句 60 字 ≈ 3 秒），
切段后第一段（十几字）合成完就开口（≈1.5 秒），剩下的段在"念第一段"的同时合成。
**合成和播放必须分两条线程**：一条线程顺序做的话，每段都要"先等合成再等播放"，
等于把两段时间加起来。

**为什么要 `tts_ting(bie)` 关别名**：MCI 的别名有上限，分段之后一条回复开 3~5 个，
不关的话几十句话之后就"开不出来"——表现为突然没声音、但程序一点错都不报。

**语气语调**：`TTS_QINGXU` 把 平静/关心/开心/兴奋/得意/委屈/困惑 各映射一组
(语速, 音调)，数值都压得很小（3~7Hz / 几个百分点）；`tts_qingli` 现在**保留句末
的。！？**，因为 edge-tts 靠它们定语调（削了问号就不上扬）。

**还能更快吗**：首声 ~1.5 秒里，1.1 秒是到微软服务器的 WebSocket 握手，
换不掉（edge-tts 每次合成都新建连接）。真要"立刻出声"，只能换 Windows 本地
SAPI（离线、0.1 秒，但音色是机器朗读腔），需要新加一个引擎开关。

### 第三十轮：方案 1+2+3（音色不变，只改"什么时候能听见"）

| 层 | 做法 | 收益 |
|---|---|---|
| 1 预合成 | 启动 20 秒后，后台把 22 条固定台词（开场/告别/打赏七档/送礼十一件/恋人）按 平静+开心 两种情绪灌进 `语音缓存/`；每次真合成都会更新 `_tts_huoyue`，预合成看到 5 秒内有活动就停着等 | 这些句子从 ~1.8s 变 **0s** |
| 2 流式 | 第一段不整段等下载：`tts_liushi()` 用 `Communicate.stream()` 边下边按 **mp3 帧边界**切，攒够 ~0.9 秒就先播一块 | 首声再省 **0.5~0.7s** |
| 3 收敛 | 段数 5→3，首段压到 12 字以内 | 少两次握手，首声更早 |

**为什么只切第一块**：实测服务器经常把整段音频"一大坨"吐过来，切碎了并不更快，
反而每多一块就多一次 MCI 开关（几十毫秒的接缝）。
**为什么必须帧对齐**：MCI 打开半帧的 mp3 会静音且**不报错**。
**为什么不能边播边往同一个文件追加**：MCI 播放期间独占锁文件（实测 PermissionError），
而且打开时就把时长算死了。
**失败兜底**：`.part` 写完才改名进缓存；流式失败会删掉半截文件，下次重新合成。
**临时块**：放在 `%TEMP%\小笨蛋_流式\`，播完就删，启动时 `tts_kuai_qing()` 再清一遍。

### 第三十二轮：撤销 1+2+3，语音退回"按标点切段"

**为什么撤**：流式切块按字节切，切点落在句子中间；首段又被硬切到 12 字、段数压到 3 ——
三件事叠起来，听感就是"一句话被剁成几截"，用户原话"断句很奇怪"。
结论写在这儿：**首声那半秒不值得拿断句换**。

**现在这条链（等于第二十九轮）**：

_mp3_kuang / _tts_kuai_mulu / _tts_huoyue / _TTS_YURE / TTS_LIUSHI_MIAO / TTS_SHOU_ZUI_CHANG`。

### 第三十七轮：表情补到 26 张 + 不重复

**张数选择的依据**（用户问"做多少合适"，给的结论）：推荐 22~26 张。
判断标准不是好看，是**重复感** —— 同一张图在一段对话里出现两次，用户立刻觉得假。
一场 15~20 句的对话大约用 5 张，池子 20 张以上重复概率才低到察觉不到。

按使用频率分配（不是平均分）：

| 情绪 | 原来 | 现在 | 理由 |
|---|---|---|---|
| 平静 | 1 | 3 | 最高频，占三成 |
| 开心 | 1 | 2 | |
| 关心 | 1 | 2 | 一张温柔、一张担忧 |
| 害羞 | 1 | 3 | 恋人线高频 |
| 委屈 / 得意 / 恋人 | 1 | 2 | |
| 兴奋 / 困惑 | 1 | 1 | 低频 |

场景款保持 11 张：招手 惊讶 偷笑 大哭 比心 生气 发呆 晚安。

**`_bq_tiao()`：最近 5 张不重复**
随机是独立的，连抽两次同一张完全可能。现在记住最近 5 张先排除；
候选被排除光时（"平静"只有 3 张）选**最久没出现**的那张 —— 不是再随机一次。
实测"平静"连抽 15 次，相邻重复 0 次。

**整池随机要过滤**：`BQ_SUIJI` 那条 35% 的随机里剔掉 恋人/生气/大哭 ——
平静的日常对话里蹦出一张爱心眼或者大哭，比没有表情更糟。

**AI 生成的两张新表**：4×2 那张表达跑偏（想要"担心"，给了"托腮"），
另补一张 2×2 拿到准确的"担心 / 恋人 / 大笑"；右下角带水印的格子一律弃用。

### 第三十八轮：表情按"场合"挑，不只看脸色

按心情挑图有个硬伤：说完"晚安"可能贴一张大笑 —— 情绪没错，场合错了。
现在加了一层场合识别，顺序是 **场合 → 心情 → 通用款随机**。

| 用户那句 | 认出场合 | 出图 |
|---|---|---|
| 晚安啦 / 我走了 | bye | 拜拜 · 晚安 |
| 我回来了 / 早上好 | hi | 招手 · 开心 |
| 今天好累啊 / 想哭 | comfort | 关心 · 关心_2 |

### 第三十九轮：输入框"聊两句就打不了字"

**先记结论：问题不在 Tk，在 Windows 那一层。**

Tk 里 `focus_get()` 一直指向输入框，但 `GetFocus()`（系统级）落到的是**主窗口的 HWND**。
两层不一致的时候，光标照样闪、按键却哪儿也不去 —— 这就是"打不了字"。

**为什么会跑到窗口上**
上一轮我给功能页写的聚焦函数是：
```python
self.win.focus_force()   # ← 先把系统焦点搬到面板窗口本身
w.focus_force()          # ← Tk 认为控件已经有焦点，这句成了空操作
```
顺序一反，就成了"焦点在窗口上、控件收不到字"。主输入框没有这套逻辑，
但只要有任何操作把系统焦点挪到窗口本身（点聊天区、回复完、切回来），
就同样卡住。

**第二次修正（同一天）**
第一版写错了：`focus_set` 只在"Tk 已经有焦点"时才有效。功能页刚销毁那一下
`focus_get()` 是 None，`focus_set` 直接失败，焦点谁也拿不到。
所以现在按这个顺序：`focus_set` → 判断 Tk 层是不是真的落在输入框上 →
不是就 `focus_force`（**先确认前台是本程序**，否则会把用户从别的软件拽回来）→
最后 `SetFocus(控件HWND)` 收口。

**功能页那边**：面板是 overrideredirect 的独立窗口，`SetFocus` 在窗口还没成为
前台的那一瞬间会被系统拒掉（返回 0、不抛异常），所以点击后 60ms / 180ms 各补一次。

**现在的做法（三处统一）**
1. `jujiao_quan()`：Tk 里 `focus_set()`，系统里 `SetFocus(entry_hwnd)` —— 直接点名控件；
2. 触发点：点输入框、点聊天区、每次回复写完（`root.after(60, _hui_jujiao)`）、按回车发送之后；
3. **看门狗** `_kan_jujiao()`：每 2 秒查一次 —— 当前台是本程序、Tk 焦点在输入框、
   而系统焦点不是输入框，就纠正回来。切到别的软件、或焦点在功能页时不碰。

**实测**（真窗口 + ctypes 读 GetFocus）
- 连发三句：焦点一直在输入框；
- 人为把焦点挪到顶层窗口 → 看门狗 1.9 秒内拉回；
- 点一下聊天区 → 焦点回到输入框（顺手做成微信那样）；
- 截图/文件对话框之后再点输入框，一次就能打字。

**关面板也要还光标**
功能页是独立 HWND，关掉之后 Windows 会把焦点交给"下一个窗口" —— 有时是主窗口本身。
`GongNengYe.guan()` 里补了 `root.after(80, zhu._hui_jujiao)`。

**这颗雷是自己埋的**
第三十五轮那个 `_yao_jujiao` 里写了 `win.focus_force()`，顺序一反就制造了
"系统焦点在窗口上、Tk 以为在控件里"的死局。教训：
**要抢焦点就 SetFocus 点名控件，别对 Toplevel 调 focus_force。**

### 第四十三轮：输入法候选窗飞到显示器左上角

四个地方都中招：对话区输入框、写作标题、整理助手标题/正文、人设框。

**根因（实测 + ctypes 逐项确认）**
1. **Tk 自己不创建系统 caret。** 它在画布上自己画闪烁光标，从不调 `CreateCaret`。
   于是 `GetGUIThreadInfo().hwndCaret` 拿到的是**别的进程/别的窗口**的 caret ——
   实测位置 (38,655)，跟我们任何输入框都无关。微软拼音这类输入法优先拿它定位候选窗，
   于是候选条跑到别人家窗口的坐标上，落在屏幕左上角。
2. 组合窗（composition window）位置每次按键、每次 FocusIn 都会被 Tk 的类绑定重算覆盖，
   设一次没用，必须在 `after_idle`（事件全跑完之后）再设一次。

**修法**：新增模块级 `ime_ding_wei(w)`，做两件事：
- 给控件建一个 **1×1 的隐形 caret**（空位图 + `HideCaret→SetCaretPos→ShowCaret`），
  不影响 Tk 自己画的闪烁光标，但给了输入法一个正确锚点；
- 设组合窗位置到光标下面。
四个入口统一接上：对话输入框 `_ime_bai_hao`、写作标题（`_xz_timu`）、
整理助手标题/正文、人设框（都在 `_deng_ji_shuru` 里统一绑了 KeyRelease/ButtonRelease/FocusIn）。

**实测**（真窗口 + ctypes 读 `GetGUIThreadInfo`）
| 输入框 | caret 归属 | caret 位置 | 组合窗 |
|---|---|---|---|
| 对话输入框 | 是控件 | (4,23) | (4,29) |
| 写作标题 | 是控件 | (4,34) | — |
| 人设框 | 是控件 | (4,18) | (4,24) |

（改前 caret 归属是「别的窗口」、位置 (38,655)。）

### 第四十四轮：候选条"先在输入框下面露一下，不到一秒又被拽回左上角"

第 43 轮只在事件之后补一次位置，用户实测还是会被拉走。写了两个 Win32 探针逐项测：

| 动作 | `GetGUIThreadInfo` 读到的 caret |
|---|---|
| 刚建好隐形 caret | 归属是本控件，坐标 (30,22) |
| **`SetFocus(hwnd)` 一次** | 归属还在，但**坐标被清成 (0,0,1,1)** |
| 焦点去别的窗口再回来 | **归属整个变成别的窗口**，坐标 (0,0) |
| 重建 `CreateCaret` | 归属抢回来，坐标恢复 |

程序里有一堆"延迟把焦点还给输入框"：`_hui_jujiao`（回完话 60ms、点聊天区 10ms）、
功能页 60/180ms 补设、2 秒看门狗。旧版每次都无条件 `SetFocus`，还用字典记着
"这个 hwnd 建过 caret 了"不再重建 —— 补完没多久又被下一次回焦抹掉，
这就是"闪一下就飞走"的全部原因。另外 64 位 Python 下没写 `argtypes`，HWND 有截断风险。

**这一轮的改法（全在 Win32 / 事件层，对话框 UI 一个像素没动）**
1. `ime_ding_wei` 重写：每次先用 `GetGUIThreadInfo` 自检"caret 还是不是我们的、
   坐标对不对"；不是就重新 `CreateCaret`（1×1 + `HideCaret` 隐藏，实测隐藏状态下
   输入法照样读得到 `rcCaret`），是就只补 `SetCaretPos`。**去掉"建过一次"的缓存**。
   组合串窗口和候选列表窗口（`ImmSetCandidateWindow` / `CFS_CANDIDATEPOS`）两个坐标都点名。
2. 所有 `SetFocus` 前先比 `GetFocus()`，已经是目标控件就**不再调用** —— 从源头减少抖动。
3. 新增 `ime_kai_shou` / `ime_shou_hu`：每个输入框一条 150ms 常驻自检，
   只在 caret 跑掉或坐标偏了才动手（正常打字零 Win32 调用，不打断拼音），
   约每 1 秒强制压一次组合窗/候选窗坐标。四个入口全部接上。
4. `_ime_api()` 统一钉死 user32/gdi32/imm32 的函数签名，64 位 HWND 不再被截断。

**实测**（把主程序这段抽出来单独跑）
| 步骤 | 结果 |
|---|---|
| 摆好 | caret 是本控件，rc=(2,21) |
| 模拟延迟回焦 `SetFocus` | rc 被清成 (0,0) ← 复现用户现象 |
| 自检修复 | rc=(2,21) |
| 焦点一进一出 | caret 归属变成别的窗口 |
| 重建修复 | 归属抢回，rc=(2,21) |
| 守护定时器 400ms | 无异常 |

`py_compile` 通过；主程序启动 16 秒无异常、窗口正常存活。

### 第四十七轮：找到真凶 —— 是程序里那句 `SetFocus(Entry)`，不是输入法

**现象（用户录像复现）**：拼音刚打下去，候选条本来正确出现在对话输入框下方，
不到一秒就被拽到**显示器左上角**，拼音也被清空。

**根因（实验证据，不是猜的）**

Tk 在 Windows 上并不是一个窗口，而是一棵树：

```
TkTopLevel（真·顶层窗口）
  └─ TkChild（root.winfo_id()）   ← GetFocus() 实际返回的就是它
        └─ TkChild（Canvas / YuanShuRu）
              └─ TkChild（Entry._nei）
```

也就是说 **`GetFocus()` 永远不可能等于 `int(Entry.winfo_id())`**（实测 Tk 8.6 / 9.0 都一样）。
程序里有两处拿这个当判据：

1. `_kan_jujiao()` 的看门狗：`if int(w.winfo_id()) != u.GetFocus(): jujiao_quan()`
   → **恒为真**，每 2 秒无条件执行一次 `jujiao_quan()`；
2. `jujiao_quan()` 末尾那句 `ctypes.windll.user32.SetFocus(int(self._nei.winfo_id()))`
   —— 把系统焦点从"顶层 TkChild"搬到"Entry 的 TkChild"。

微软拼音对"焦点窗口换人"的反应是：**结束当前组合**（组合串被清空），
组合窗坐标随之清零 → 下一次落点算在原点 → 屏幕左上角。
这就是"先在下方闪一下、立刻被拽走"。

**对照实验（同一个输入框结构，只差这一句）**
